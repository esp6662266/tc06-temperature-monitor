# TC-06 0.6.0 업데이트와 OCR 복구

## 최초 설치·연결

기존 0.5.0에는 원격 업데이트 코드가 없다. 현장 사용자가 수집기를 종료한 뒤 0.6.0 설치판을 최초 한 번 설치한다. 이 작업으로 현장 PC에 설치했다고 주장하지 않는다. 수집기만 갱신하며 HMI/PLC/Windows 재부팅을 하지 않는다.

1. 온도 사이트의 일반 화면에서 **수집기 업데이트**를 연다: `/updates.html`.
2. 관리 코드를 입력한다. 이 코드는 온도 조회·업로드와 별개다. 브라우저 URL/쿠키/localStorage/sessionStorage에 넣지 않으며 연결 해제 시 메모리에서 지운다.
3. **새 PC 연결**에 수집기의 PC 식별자를 입력하고 연결 코드를 발급한다.
4. 수집기 GUI의 **원격 업데이트 연결**에 발급 코드를 입력한다. 서버 주소와 PC 식별자는 온도 수집 설정과 일치해야 한다.
5. 웹에서 해당 PC 버전과 마지막 응답 시각을 확인한다. 연결 코드 발급은 업데이트 실행이 아니다.
6. 새 서명된 버전이 게시되고 PC가 연결돼 있을 때 **업데이트 적용 → 업데이트 실행**으로 요청한다.

현재 버전과 배포 버전이 같거나 PC가 응답하지 않거나 유효한 서명된 배포물이 없으면 적용 버튼은 비활성이다. 새 버전 확인은 30분 간격, 서버 명령·상태 확인은 15초 간격이다. 프로그램이 종료됐거나 Windows에 로그인하지 않은 상태에서는 원격 업데이트할 수 없다.

## 적용과 복구

- 다운로드는 수집 중 수행한다. 공식 저장소의 정확한 버전별 포터블 URL만 허용한다. Ed25519 서명·SHA-256·파일 크기·압축 해제 용량을 대조한다. 공식 GitHub 다운로드 CDN 외 리디렉션은 차단한다.
- 다운로드는 약 4 MB/s로 제한한다. 크기 상한은 압축 300 MB, 해제 900 MB다. 설치판·포터블·영문 OCR 런타임이 모두 포함된 전체 폴더를 사용한다.
- 관리 명령은 장치에 귀속된 UUID/nonce와 10분 만료를 가지며 조건부 쓰기로 한 번만 수령한다. 적용 직전에도 서버에서 권한을 재확인한다. 관리 버튼 요청은 별도 bearer 인증과 2분짜리 일회용 nonce가 필요하며 분당 30회로 제한한다.
- 준비된 뒤 수집기 스레드가 끝나기를 기다리고 별도 도우미가 교체한다. 합성 내장 OCR 검사가 통과하고 새 GUI가 시작돼야 성공이다. 수집 설정이 있으면 OCR 작업이 준비되고 서버가 저장을 확인한 뒤 시작 확인이 끝난다. 이는 실제 OCR 정확도·현장 영상 검증과 다르다.
- 실패하면 이전 실행 경로를 복구하고 이전 수집기를 다시 시작한다. 교체 중 전원 차단/도우미 종료 후 다음 실행 시 미완료 전환을 복구한다. 실행 중인 버전 폴더를 덮어쓰지 않는다.
- 웹에 완료/실패/이전 버전 복구, PC 버전과 마지막 응답 시각, 교체·확인 소요 시간을 표시한다. 이 시간은 프로그램 전환 구간이며 실제 측정 간격과 다를 수 있다.
- CPU·디스크 영향 0 또는 무중단 수집을 보장하지 않는다. 누락된 분의 값을 추정해 실측으로 저장하지 않는다.

## 로컬 데이터와 진단

기존 `%LOCALAPPDATA%\TC06Monitor\config.json`, `history.sqlite3`, 전송 대기 자료를 보존한다. 다음 자료도 이 사용자 폴더 아래에만 저장하며 GitHub에 올리지 않는다.

- `diagnostics/failures.jsonl`: 상태 변화·30초 이상 지속 실패·복구, 후보 숫자, 신뢰도, 시각, 입력 크기, 처리 시간, 버전. 300 KB × 3개로 회전한다.
- `diagnostics/crop-*.png`: 온도 영역만 최대 640×160. 최소 30초 간격, 최대 24장·총 5 MB. 라벨/영역 미검출 시 전체 화면 대신 텍스트 상태만 기록한다.
- `update-link.json`: 이 PC의 업데이트 전용 연결 코드. Windows 현재 사용자 폴더 권한을 사용한다. 온도 API에 보내거나 온도 이력에 넣지 않는다.
- `updates/versions/<버전>`: 검증한 새 실행파일 전체. 이전 버전은 복구용으로 유지하며 자동으로 지우지 않는다. 디스크 부족 시 업데이트 준비를 거부한다.
- `updates/active.json`, `transaction.json`, `result.json`: 실행 경로·교체 진행·결과. 사용자 데이터 DB를 교체하지 않는다.

평소 OCR은 2초 간격이다. 실패 초기에는 3초, 30초 이상 실패하면 10초 간격으로 **새 프레임**을 읽는다. 원본 시계 확인·동일 엔진의 두 분할 결과 일치·픽셀 자릿수/소수점·시작/복구/큰 변화의 다음 원본 시계 확인을 유지한다. 느슨한 판독으로 성공을 만들지 않는다. 저장은 60초 간격이며 실패(null) 기록이 저장된 뒤 정상으로 복구되면 실제 캡처 시각의 확인된 값 한 건을 즉시 저장한다. 짧은 실패/성공 반복으로 저장 빈도를 높이지 않는다.

## 운영 설정과 다음 릴리스

관리 코드: Netlify **TC-06 전용 사이트**의 Functions 환경 변수 `TC06_UPDATE_ADMIN_TOKEN` (영문·숫자·하이픈·밑줄 8~100자; PC별 연결 코드는 별도로 32바이트 난수 사용). Free 계정에서는 세부 scope/Secret 옵션 대신 사이트의 표준 환경 변수로 설정하며, 값 자체를 소스나 웹 JS에 넣지 않는다. 운영 반영은 `netlify deploy --prod --context production`으로 배포한 뒤 인증 응답을 확인한다. 설정이 없으면 업데이트 API 전체가 503으로 비활성이다. 온도 조회·수신 API는 계속 공개다.

배포 서명: 검증된 Windows 포터블 산출물을 내려받아 로컬 비공개 키로 `scripts/sign-update.py <포터블ZIP> <버전> --key-file .private-update/release-signing.key`를 실행한다. 별도 승인된 CI 환경에서는 환경 변수 `TC06_SIGNING_KEY`에 32바이트 Ed25519 비공개 키의 base64를 전달해 빌드 후 서명할 수도 있다. 현재 저장소 workflow는 기존 수동 빌드를 유지하며 비공개 키를 전달하지 않는다. 공개 키는 `collector/tc06/trust.py`, `server/update-trust.mjs`에 고정돼 있다. 키를 바꿀 때는 기존 프로그램의 신뢰 키 이전 절차가 필요하며 임의로 재생성하지 않는다.

이 작업의 최초 비공개 키·관리 코드 원본은 로컬 `.private-update/` (Git 제외, 폴더 700/파일 600)에 보관한다. 재발급 또는 분실 복구 전에 기존 운영 값·연결을 확인한다. 비공개 자료를 소스 ZIP이나 공개 보고서에 포함하지 않는다.

1. `package.json`, lockfile, `collector/tc06/recovery.py`의 버전을 함께 올린다.
2. Python/Node/브라우저 검사를 수행하고 GitHub 수동 **Build Windows installer**를 실행한다.
3. Windows 설치→외부 Python/OCR 제외→내장 합성 OCR/GUI→삭제 후 자료 보존→실제 패키지 프로세스 교체/손상 파일 롤백 검사가 모두 통과해야 로컬에서 서명한다.
4. 빌드 결과의 설치 EXE, 포터블 ZIP, `update-manifest.json`, 해시와 검증 보고서를 같은 `v<버전>` GitHub Release에 게시한다. 이미 게시된 버전의 파일을 바꿔치기하지 않는다.
5. 현장 에이전트가 새 릴리스를 발견해 웹에 표시한 뒤 관리자가 적용을 요청한다. 최초 설치·연결과 실제 현장 시험은 별도다.

서명 구현 참고: [cryptography Ed25519](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/). 명령 경쟁 보호는 [Netlify Blobs conditional writes](https://docs.netlify.com/build/data-and-storage/netlify-blobs/)를 사용한다.
